# Decisions made to complete interface 1

Each entry is a choice this interface needed and the blueprint did not make, in the form of
`spec/engine/decisions.md`. They are defaults, not settled policy. Entries marked **needs review** affect customers
and should be confirmed before anyone builds on them. Numbers are stable.

## API keys

The owner's decision (2026-09-17): the venue has API keys, and a key may call the money functions only if it is
flagged to. What follows is how.

| # | Decision | Why | |
|---|---|---|---|
| G-1 | A key is an ID and a secret. The ID is `ak_` and 16 lower-case hex digits, public, and appears in lists and audit records. The secret is 64 lower-case hex digits from the operating system's random source (256 bits), shown once when the key is created and never stored. The two travel together as `<keyId>.<secret>`. | The ID lets a person and an auditor say which key did something without handling a secret. A prefix makes a key recognisable in a configuration file or a leak report. 256 bits cannot be guessed, and one string is easy to paste into every protocol's one credential field. | |
| G-2 | The identity service stores `SHA-256("venue-api-key/1:" + keyId + ":" + secret)` and compares hashes in constant time. It does not use a password hash such as Argon2. | A password hash is slow to make guessing a low-entropy password expensive; a 256-bit random secret cannot be guessed at any speed, and a slow hash would cost every verification. Salting by key ID and a version tag keeps one hash from standing for another key or scheme. This is how widely used API-key services store theirs. | |
| G-3 | Permissions are `read`, `trade`, `transfers` and `keys`. Every key holds `read`. | The owner asked for money movement to be a flag of its own; `trade` and `keys` separate the other two things a stolen key could do harm with. A key that can act for an account but not see it is of no use to anyone and would only make logging in to a private session, which streams the account, refusable; so `read` is required rather than optional, and still named, so that a later read-free key needs no contract change. **needs review** | |
| G-4 | Requests for quote and quotes need `trade`; reading one request needs only `read`. | Asking for a quote lists a parlay and a quote is a resting order: both act on the market. | |
| G-5 | Keys are managed over REST (`/v4/keys`) with a credential holding `keys`: a dev token in a test environment, or a key made with `keys`. A key cannot create a key with a permission it lacks, or one that expires after it does. Revoking a key does not revoke the keys it made. | A key with `keys` is how a firm delegates without handing out its dev token or, later, its login. Without the subset and expiry rules a limited key could mint an unlimited one. Cascading revocation would make revoking a person's console key silently stop a production bot; the list says which key made which (`createdBy`), so an owner can revoke both on purpose. | |
| G-6 | Keys cannot be changed, only revoked and replaced. At most 20 keys per account are neither revoked nor expired. | An unchangeable key is one whose permissions an audit record can be read against for its whole life. The cap bounds the store and the list, and is far above what a firm uses. | |
| G-7 | The identity service is a process of its own, owns the key store (an append-only file it replays at start) and answers the gateways over an internal HTTP API; a gateway remembers each answer for 5 seconds. Revocation and expiry take effect within 10 seconds: at most 5 on REST, and a private session using the key is closed within 10. | The gateway holds nothing a failover could lose, so the store cannot live in it. Asking the service on every request would put a network round trip on every order; a short cache keeps that to one every few seconds per key, and a stated bound is what a firm revoking a leaked key needs to know. A background check of the keys that sessions hold is what makes a long-lived session honour a revocation without a round trip per order. | |
| G-8 | A key's last use is recorded when a gateway asks about it, and written to the store at most once a minute per key. | Free: the gateway asks at most every few seconds while a key is in use. A write per request would make the store grow with trading. | |
| G-9 | Dev tokens keep working as a legacy path in test environments: each acts as its account with every permission, is not a key, and can be refused with `--dev-tokens false`. | The demo, the bots, the tests, the FIX console and the web page all use them, and the first key of an account has to be made with something. Not making them keys keeps them out of the store and out of the key list, where they could be revoked by accident. | |
| G-10 | FIX takes a key either as Username (553) the key ID and Password (554) the secret, or as the whole credential in Password. A key without `trade` may log on: its orders, cancels and replaces are rejected (`FORBIDDEN` in Text), and it can list securities. | Firms put the key ID where the login name goes and the secret where the password goes; accepting the combined form too keeps a dev-token firm's configuration shape. A read-only session is how a firm checks connectivity and reference data with a key that cannot trade, so refusing its Logon would take that away and gain nothing. | |
| G-11 | An unknown key, a wrong secret, a revoked key and an expired key are all 401 `UNAUTHORIZED`; the message says revoked or expired only when the secret was right. | Whoever holds the secret learns why the key stopped working; whoever guesses learns nothing about which key IDs exist. | |
