# Decisions made to complete interface 1

Each entry is a choice this interface needed and the blueprint did not make, in the form of
`spec/engine/decisions.md`. They are defaults, not settled policy. Entries marked **needs review** affect customers
and should be confirmed before anyone builds on them; **reviewed** with a date is one the owner has since confirmed.
Numbers are stable.

## API keys

The owner's decision (2026-09-17): the venue has API keys, and a key may call the money functions only if it is
flagged to. What follows is how.

| # | Decision | Why | |
|---|---|---|---|
| G-1 | A key is an ID and a secret. The ID is `ak_` and 16 lower-case hex digits, public, and appears in lists and audit records. The secret is 64 lower-case hex digits from the operating system's random source (256 bits), shown once when the key is created and never stored. The two travel together as `<keyId>.<secret>`. | The ID lets a person and an auditor say which key did something without handling a secret. A prefix makes a key recognisable in a configuration file or a leak report. 256 bits cannot be guessed, and one string is easy to paste into every protocol's one credential field. | |
| G-2 | The identity service stores `SHA-256("venue-api-key/1:" + keyId + ":" + secret)` and compares hashes in constant time. It does not use a password hash such as Argon2. | A password hash is slow to make guessing a low-entropy password expensive; a 256-bit random secret cannot be guessed at any speed, and a slow hash would cost every verification. Salting by key ID and a version tag keeps one hash from standing for another key or scheme. This is how widely used API-key services store theirs. | |
| G-3 | Permissions are `read`, `trade`, `transfers` and `keys`. Every key holds `read`. | The owner asked for money movement to be a flag of its own; `trade` and `keys` separate the other two things a stolen key could do harm with. A key that can act for an account but not see it is of no use to anyone and would only make logging in to a private session, which streams the account, refusable; so `read` is required rather than optional, and still named, so that a later read-free key needs no contract change. **reviewed 2026-09-21** | |
| G-4 | Requests for quote and quotes need `trade`; reading one request needs only `read`. Answering requests as a responder also needs `respond` (G-12). | Asking for a quote lists a parlay and a quote is a resting order: both act on the market. | |
| G-5 | Keys are managed over REST (`/v4/keys`) with a credential holding `keys`: a dev token in a test environment, or a key made with `keys`. A key cannot create a key with a permission it lacks, or one that expires after it does. Revoking a key does not revoke the keys it made. | A key with `keys` is how a firm delegates without handing out its dev token or, later, its login. Without the subset and expiry rules a limited key could mint an unlimited one. Cascading revocation would make revoking a person's console key silently stop a production bot; the list says which key made which (`createdBy`), so an owner can revoke both on purpose. | |
| G-6 | Keys cannot be changed, only revoked and replaced. At most 20 keys per account are neither revoked nor expired. | An unchangeable key is one whose permissions an audit record can be read against for its whole life. The cap bounds the store and the list, and is far above what a firm uses. | |
| G-7 | The identity service is a process of its own, owns the key store (in PostgreSQL since 2026-09-17: core/store/decisions.md, S-13 to S-16) and answers the gateways over an internal HTTP API; a gateway remembers each answer for 5 seconds. Revocation and expiry take effect within 10 seconds: at most 5 on REST, and a private session using the key is closed within 10. | The gateway holds nothing a failover could lose, so the store cannot live in it. Asking the service on every request would put a network round trip on every order; a short cache keeps that to one every few seconds per key, and a stated bound is what a firm revoking a leaked key needs to know. A background check of the keys that sessions hold is what makes a long-lived session honour a revocation without a round trip per order. | |
| G-8 | A key's last use is recorded when a gateway asks about it, and written to the store at most once a minute per key. | Free: the gateway asks at most every few seconds while a key is in use. A write per request would make the store grow with trading. | |
| G-9 | Dev tokens keep working as a legacy path in test environments: each acts as its account with every permission, is not a key, and can be refused with `--dev-tokens false`. | The demo, the bots, the tests, the FIX console and the web page all use them, and the first key of an account has to be made with something. Not making them keys keeps them out of the store and out of the key list, where they could be revoked by accident. | |
| G-10 | FIX takes a key either as Username (553) the key ID and Password (554) the secret, or as the whole credential in Password. A key without `trade` may log on: its orders, cancels and replaces are rejected (`FORBIDDEN` in Text), and it can list securities. | Firms put the key ID where the login name goes and the secret where the password goes; accepting the combined form too keeps a dev-token firm's configuration shape. A read-only session is how a firm checks connectivity and reference data with a key that cannot trade, so refusing its Logon would take that away and gain nothing. | |
| G-11 | An unknown key, a wrong secret, a revoked key and an expired key are all 401 `UNAUTHORIZED`; the message says revoked or expired only when the secret was right. | Whoever holds the secret learns why the key stopped working; whoever guesses learns nothing about which key IDs exist. | |
| G-12 | `respond` is a permission of its own: subscribing to requests for quote (`subscribeRfqs`, `unsubscribeRfqs`), reading those open (`GET /v4/rfqs`), and attaching a quote, which needs `trade` too. It is checked by the gateway in addition to, never instead of, the parlay service's approval of the account; a key without it is refused even for an approved account. Dev tokens hold it. A key made with `keys` may give it only if it holds it (G-5). | Approval says an account may make markets in parlays; the permission says which of its programs does. A firm's reporting script or a trading bot's key should not start receiving other accounts' requests because the account was approved, and seeing requests is information a key could leak even without trading. Keeping the approval with the parlay service's operator and the permission with the key's owner lets each be withdrawn alone. | |

## Several gateways

A venue runs gateway processes side by side, public and private apart or together (README, public and private). These
are what that needed.

| # | Decision | Why | |
|---|---|---|---|
| G-13 | Flood and logon limits stay in each gateway process's memory and are not shared: a message bucket per session, a REST bucket per account and a logon bucket per account, per process. With N gateways an account can reach N times the REST and logon limits. | Blueprint §12 puts flood protection at the edge, in memory, and never in the journal; sharing buckets would need a store every request consults, which is the round trip the edge exists to avoid. The limits guard gateways against floods, not accounts against themselves, and are set far above legitimate use; what bounds a customer is a rule limit, which is sequenced. An operator who wants a tighter venue-wide bound divides the per-gateway limit by the number of gateways. Sharing the buckets (e.g. GCRA state in Redis) was weighed and not taken: it would put a network round trip and a new failure mode on every order for the one limit that multiplies, REST per account. High-volume market makers are expected to be given gateways of their own, where per-gateway limits are per-firm limits; an exact venue-wide promise to a customer belongs in a sequenced rule limit. Confirmed 2026-09-17. | |
| G-14 | An amendment or cancel naming an order ID above every order ID the gateway's feed has delivered waits up to 2 s for the feed, then is sent; one still undelivered is refused with 503 `UNAVAILABLE` and nothing is sent. An ID the feed has passed that does not rest is 404 at once. | Order IDs rise in the order the engine accepts orders within a group (E-2.8, E-9.8), so an ID above the highest delivered is one the gateway has not heard of yet, never one that has gone. A client that places through one gateway and cancels through another, or reconnects to a gateway still replaying, would otherwise be told a live order does not exist. Waiting on the feed rather than guessing keeps the gateway validating against what the journal says. Two seconds is far beyond a healthy feed's lag and short enough that a mistyped ID is answered promptly; 503 rather than 404 because the order may well exist. | |
| G-15 | A browser page served from another origin is answered only if its origin is in `--allowed-origins`, which is empty by default; the origin is echoed rather than `*`, `OPTIONS` from an allowed origin is answered 204 and from anywhere else 404, and the WebSockets are not origin-checked. | The venue serves its own page today, so nothing needs this until a front end is built somewhere else, and then it needs exactly the origins it runs on. Echoing an allow-listed origin keeps the answer readable by one page rather than every page, which matters while the credential is a bearer token. The sockets need no check because no credential is ambient: a session is nobody until it sends `login`, so a page on another site can open one and learn nothing. | |\n
| G-16 | A member is an email, an Argon2id password hash and an account of their own, kept by the identity service; logging in answers a session credential (`vs_`) that works everywhere an API key does and lasts 30 days. It holds read, trade and keys over that account, and gains transfers once the address has been proved by a code sent to it. Signing up, proving an address, asking for a new password and logging in are the only requests the gateway takes from nobody, and are limited per client address at the logon rate. | The apps need a way for a person to sign in, and interface 6 is not specified yet; this is the smallest thing that lets them, built the way the rest is (a credential the gateway verifies through the identity service, remembered for seconds). Making it a credential of the same shape meant the gateway, the sockets and the audit log needed almost nothing new. 30 days is what an app used daily can hold without asking again; a token taken from a device stops working without anyone doing anything. Withholding transfers until the address is proved is what makes proving it worth anything: a member can look around and trade straight away, and no money moves to or from an address the venue has never had an answer from. The per-address limit is there because a login endpoint is where passwords are guessed. | **reviewed 2026-09-21** |
| G-17 | Nothing in the member flows says whether an address is already a member's: signing up, asking for the verification message again and asking for a new password all answer `{"checkYourEmail": true}`, and all three write to the address either way — the code, or a note that somebody tried with an address that has no account (or already has one). A wrong password and an address nobody has are refused in the same words, and a password is hashed against a dummy PHC when there is no member so the two take the same time. | Otherwise the sign-up route is a way to ask the venue which of a list of addresses trade here, which is worth money to whoever asks and is nobody's business. The cost is that a person who mistypes their own address is told nothing; the message sent to the address they did type is what closes that, which is why mail goes out on the branch where nothing was made. | **reviewed 2026-09-21** |
| G-18 | Five wrong passwords in a row lock a member for fifteen minutes, on the member rather than on the address the attempts came from, and the member is told by mail that it happened; setting a new password lifts it. A second factor is TOTP (RFC 6238, six digits, thirty seconds, one step of drift), with ten single-use recovery codes made when it is confirmed; the step a code was accepted at is written down so a code cannot be used twice. | Locking on the address does nothing against guessing spread over many addresses, which is how it is actually done. Locking on the member does, and its cost is real and accepted: anyone who knows an email can keep its owner out for fifteen minutes, which is why the lock is short, why the member is told, and why a password reset — which proves the address — lifts it rather than waiting it out. Recording the step is what makes a code single-use; without it a code read off a screen works for the rest of its window. The owner's decision (2026-09-21): the lock stays on the member. What it costs is harassment of somebody whose address is already known, which is worth less than letting a guess at their password through, and probing for one particular address is a good deal more theoretical than guessing spread across many. | **reviewed 2026-09-21** |
| G-19 | The identity service queues the mail it would send in `outbox_mail` and answers `GET /v1/mail` with it, and the gateway passes that through as `GET /v4/mail` — but only where the service was started with `--show-mail`, which is off by default. | A demo has no mail provider, and the codes have to reach somebody or none of these flows can be shown or tested; the treasury's fake bank stands in for a real bank the same way. Making it a flag that is off by default, rather than a build or an environment name, is what keeps it from following the code into a venue whose addresses are real: there the messages would hand every code to whoever asked for them. The owner's decision (2026-09-21): this stands for now, and what should replace it is a mail provider the venue can really post through, so that no route serves what was sent — an endpoint that shows a code is an endpoint that shows a way in, however well it is guarded. | **reviewed 2026-09-21** |
| G-20 | Each pull request gets a venue of its own, and an app chooses between them with `GET /v4/bootstrap`: everyone is told about the live venue, and only a member the records mark as staff is told the rest. A session belongs to the venue that issued it and to no other — the environments keep separate identity services and separate databases — so a developer signs in to a test environment separately. Staff is a member attribute set only against the records by an operator, never over the API. | A test environment runs a branch nobody has reviewed. If it could verify live credentials, every branch could be written to collect them and review would be happening after the damage rather than before it; keeping the records separate makes that impossible rather than merely forbidden, which is the only version worth relying on. The bootstrap is then discovery and not authorization, and is treated as such: it cannot protect an environment, because a URL is not a secret, so each one defends itself. What withholding the list does buy is that internal addresses are not advertised and nobody wanders onto a venue whose money is imaginary believing it is real. Staff is not a permission because permissions are what a credential may do with an account, and it has no API because the one thing that must never happen is a member arranging to be told about internal venues. | **reviewed 2026-09-21** |

## Subaccounts

A market maker's decision (2026-09-25): accounts need to be organised into families — a liquidity-provision book and a
scalping book, say — that share an owner but cannot trade against one another, and money needs to move between them.

| # | Decision | Why | |
|---|---|---|---|
| G-21 | An account may carry a `masterAccountId` (`spec/engine/decisions.md`, D-33); an account with one is a subaccount and an account with none may be named as another's master. This is the *account's* property, not the key's, so it is asked for on its own (`GET /v1/accounts/{accountId}` inside identity, `Identity::account_master` in the gateway) rather than riding along on `/v1/verify` — a key's own answer already carries enough, and most calls never need to know a caller's family at all. `POST /v4/subaccounts` makes one, `GET /v4/subaccounts` lists an account's own; both need `keys` on the master's own credential (G-5's pattern), never on the subaccount's. Since a fresh subaccount has no dev token and no session to make its first key with, `POST /v4/subaccounts/{accountId}/keys` (and its `GET`/`DELETE`) let the master do it instead, gated on being asked about that account's master fresh, on every call — not cached, and not assumed from who created it. | Market makers need to split trading into accounts a firm's own strategies cannot wash-trade against (D-33), while keeping keys and permissions exactly as granular as they are today (G-1–G-12) — a subaccount is a first-class account with its own keys, not a view onto the master's. Requiring the master's own credential to mint a subaccount, and its first key, mirrors why a key cannot mint one with permissions it lacks (G-5): a subaccount that could spawn siblings could be used to escape the family it was put in to be walled off from. The key-bootstrap route was not foreseen when this decision was first drafted — it surfaced only once subaccounts were built and there was no way to actually use one — and is recorded here rather than as an afterthought, since a subaccount nobody can get a key for is not a feature. Implemented and tested (`core/identity/src/store.rs`, `core/gateway/src/identity.rs`). Confirmed 2026-09-25. | |
| G-22 | `POST /v4/transfers` gains a transfer with `"kind": "internal"` and a `toAccountId`, needing `transfers` on the caller's key as any transfer does (G-3); the gateway refuses it with 403 `FORBIDDEN` unless both accounts share a master (or one is the master and the other its subaccount) — checked fresh against identity on every request, never cached the way a credential's verdict is. Both accounts must already be known to the treasury, exactly as a withdrawal's source must be (a deposit through the destination's own key is how a fresh subaccount opens). The treasury runs it as a `RECLAIM` from the source and a `GRANT` to the destination (D-34), with no call to the fake bank and no `bank:fbo_omnibus` leg — but *with* a holding account, `transit:internal_transfers`, exactly like a deposit's or withdrawal's: the reclaim and the grant are still two commands applied at two separate moments (and possibly by two different sequencer groups), so the ledger needs somewhere to keep the money balanced in between, the same reason `transit:deposits` and `transit:withdrawals` exist. Implemented and tested (`core/treasury/src/treasury.rs`, `core/gateway/src/rest.rs`); it settles in one `step()`, with no bank round trip to wait out. | Reusing `/v4/transfers` and the existing reclaim/grant machinery (E-7.2) means no new engine command, no new journal template, and no new failure mode beyond the ones deposits and withdrawals already have; the only new checks are the family check and skipping the bank. The no-transit-account idea in this entry's first draft did not survive contact with the implementation: without one, the ledger would be unbalanced for however long the reclaim and the grant are apart, which is exactly the gap a transit account exists to cover for a deposit or a withdrawal too — there was never anything special about *those* needing one and this not. A separate route was considered and rejected: a customer already has one place to look for transfer history, and an internal move is still money leaving one account's available cash and arriving in another's, which belongs in the same ledger and the same list. Confirmed 2026-09-25 — the page for doing this by hand is still a Product/Design piece, not specified here; this entry covers only the API and the ledger. | |

## IP allow-listing and mail

The owner's decision (2026-09-25): a key may be restricted to the addresses it is expected to be used from, and the
venue needs to be able to really mail somebody rather than only queue what it would have sent.

| # | Decision | Why | |
|---|---|---|---|
| G-23 | A key may carry a list of allowed IPv4/IPv6 addresses and CIDR ranges, set when it is made and changed by revoking and remaking with `keys` (G-6's "cannot be changed, only revoked" applies here too); an empty list means unrestricted, matching every key made before this existed. The gateway checks the request's real client address — resolved through `TrustedProxies` exactly as flood protection already resolves it (`core/gateway/src/forwarded.rs`, G-13), never the raw socket address behind an untrusted proxy — against the key's list on every REST call, and at logon for a WebSocket or FIX session. A list with entries and no match is 403 `FORBIDDEN`, worded so a caller cannot tell whether the key exists versus is merely off-list (as G-11 does for a wrong secret). A session already open when its key's list changes is closed within 10 seconds, on the same background recheck that already closes one on revocation (G-7). | Scoping to the key rather than the account was the owner's call: a firm runs bots from more than one location on one account, and a per-account list would force them to share a list that is the union of every server's address, which defeats the point. Reusing the trusted-proxy client address is what keeps this from being trivially bypassed by an unsolicited `X-Forwarded-For`; a raw socket address would instead be wrong for every deployment that already sits behind a load balancer. Closing a live session within the same 10-second bound as a revocation, rather than only checking at logon, is what makes a whitelist change actually take effect — a stolen key already in use from off the list is exactly the case this exists for. **needs review** | |
| G-24 | An IP whitelist changed (created, edited or cleared) joins the list of events a member is mailed about (G-19: address proved, password set, new sign-in, password changed, second factor added or removed, recovery code used, account locked), through the same `outbox_mail` queue. Separately, and needed for any of those to reach anyone outside a demo: the identity service sends through Amazon SES rather than only queuing. | An IP whitelist change is exactly the kind of event G-19 already mails for — one that, done by an attacker rather than the owner, is itself the attack — so it belongs in the same list for the same reason and costs nothing new, since the mechanism already exists. SES over a dedicated transactional provider (Postmark was the alternative considered) because the venue already runs on AWS end to end (`deploy/aws/`: Route53, cert-manager, Terraform) — SES reuses the account, the Route53 zone for SPF/DKIM/DMARC, and the existing IAM/Terraform pattern, rather than standing up a new vendor relationship and a new secret for one. The cost is SES's sandbox limits and reputation warm-up, which a dedicated transactional provider would not have; accepted because every one of these messages is a security notice, not marketing mail, and volume is low. **needs review** — needs the account owner to request SES production access and verify the sending domain before this can be built against; recorded here so the choice is made and reviewable while that happens. | |
| G-25 | Every gateway with an identity service and an ingress resends `SetMasterAccount` (E-7.13) for every subaccount identity holds, once a minute (`core/gateway/src/identity.rs`, `reconcile_subaccounts`), from a new venue-wide `GET /v1/subaccounts` inside identity. There is nothing to compare first and nothing left open for an operator, unlike the treasury's own reconciliation (`core/treasury/README.md`): the command is idempotent (E-7.1), so a resend of one already applied costs one round trip and changes nothing, and every gap the sweep can see, it closes in the same pass. Redundant across several gateways (G-13) — each does its own sweep — but harmless, for the same reason. | `POST /v4/subaccounts` (G-21) does two things — commit the subaccount in identity, then tell the engine — and a gateway that dies between them leaves identity certain of a family the engine has never heard of, which is exactly the gap subaccounts exist to close. The treasury's reconciliation exists because money can genuinely disagree three ways (its own records, the bank, the journal) and some breaks need a person to look at a statement; here there is one small fact (does the engine know this account's master) and one always-safe fix (tell it again), so building the same breaks-and-runs machinery for it would be solving a harder problem than the one this has. A minute matches the treasury's own default cadence and is not tied to anything about subaccounts specifically. Implemented and tested (`core/gateway/src/identity.rs`: `reconciliation_protects_a_subaccount_the_gateway_never_told_the_engine_about` forces the gap by committing a subaccount in identity without telling the engine, shows the family trading against itself before the sweep runs, and shows it blocked after one sweep). Confirmed 2026-09-25. | |
