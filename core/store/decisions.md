# Decisions made to move the services' records into PostgreSQL

Each entry is a choice the move needed and the blueprint did not make, in the form of `spec/engine/decisions.md`. They
are defaults, not settled policy. Entries marked **needs review** affect customers or money and should be confirmed
before anyone builds on them. Numbers are stable.

The owner's decisions (2026-09-17): real databases now, PostgreSQL first (object storage for the archive and ClickHouse
for history later, Valkey deferred); hosting pluggable between self-hosted and managed (RDS, Aurora) by configuration
alone, with no cloud-specific code; DevOps decides which later.

## Foundation

| # | Decision | Why | |
|---|---|---|---|
| S-1 | The client is `postgres` 0.19 (the synchronous face of `tokio-postgres`, by the same maintainer), with TLS through `postgres-openssl` against the system's OpenSSL. A small pool of its own (`Database::get`) rather than `r2d2`. | The services are threads with blocking I/O; an async client would bring a runtime into each of them for nothing. `postgres` is the most used PostgreSQL client in Rust outside the async frameworks, and passes `cargo deny` with two narrow allowances: Linux targets only, and syn 2 for OpenSSL's build-time macro. The rustls alternative brought five duplicate crates and ISC-licensed code. A pool is forty lines; `r2d2` would add a scheduled thread pool and still need the broken-connection handling. | |
| S-2 | Migrations are code (`Migration` lists in each service), applied at every start under an advisory lock in one transaction, with a checksum per migration; each service also has a `migrate` subcommand that applies them and exits. A changed migration, or a database newer than the build, stops the service. | At start is what keeps a laptop, a test and an ephemeral namespace from needing a separate step, and is safe because it is idempotent and locked. The subcommand is there for an environment that wants DDL run by a job with rights the service does not hold. Refusing a newer database is what keeps an old build rolled back onto a migrated schema from writing rows it does not understand. Down migrations are not written: a rollback is a new forward migration. | |
| S-3 | Each service has its own database, role and schema: `treasury`, `identity`, `parlays` and `oracle`. In the chart they share one PostgreSQL server; in production each URL may name a server of its own. The schema is named after the service in every case, and the role owns only its own database. | The blueprint asks for one PostgreSQL per domain (§18), with the ledger's the strictest. A database per service keeps that a change of host name rather than a data move, and a role per database makes "no service reads another's tables" a privilege rather than a convention. The fixed schema name keeps tests (a schema each on one server) and production the same code. | |
| S-4 | TLS defaults to libpq's `prefer`; `verify-full` with a CA file is the setting for any database reached over a network the venue does not control, managed ones included. The in-cluster server of the chart runs without TLS. | `prefer` connects to a laptop's server and to a managed one alike, which is what "configuration only" asks. It does not authenticate the server, so the chart's values for an external database say to set `verify-full`. The in-cluster server is reached over the pod network, which network policy confines to the owning services. | |
| S-5 | Database tests run against a real server when `VENUE_TEST_DATABASE_URL` is set, each in a fresh schema, and print a `skipping` line otherwise. `./check` starts one in a container (the chart's image, pinned by digest, on loopback, `fsync=off`) when Docker is usable and removes it when it ends. | Unit tests keep an in-memory store and stay fast; what only a database can show (constraints, triggers, transactions, reconnecting) is tested on one. A schema per test lets tests run in parallel on one server. | |
