# Decisions made to move the services' records into PostgreSQL

Each entry is a choice the move needed and the blueprint did not make, in the form of `spec/engine/decisions.md`. They
are defaults, not settled policy. Entries marked **needs review** affect customers or money and should be confirmed
before anyone builds on them. Numbers are stable.

The owner's decisions (2026-09-17): an established migration framework with rollback rather than a runner of our
own (S-2); real databases now, PostgreSQL first (object storage for the archive and ClickHouse
for history later, Valkey deferred); hosting pluggable between self-hosted and managed (RDS, Aurora) by configuration
alone, with no cloud-specific code; DevOps decides which later.

## Foundation

| # | Decision | Why | |
|---|---|---|---|
| S-1 | The client is `postgres` 0.19 (the synchronous face of `tokio-postgres`, by the same maintainer), with TLS through `postgres-openssl` against the system's OpenSSL. A small pool of its own (`Database::get`) rather than `r2d2`. | The services are threads with blocking I/O; an async client would bring a runtime into each of them for nothing. `postgres` is the most used PostgreSQL client in Rust outside the async frameworks, and passes `cargo deny` with two narrow allowances: Linux targets only, and syn 2 for OpenSSL's build-time macro. The rustls alternative brought five duplicate crates and ISC-licensed code. A pool is forty lines; `r2d2` would add a scheduled thread pool and still need the broken-connection handling. | |
| S-2 | Migrations are plain SQL files per service, `migrations/<version>_<name>.sql` in Atlas's layout with its `atlas.sum` beside them, forward-only, embedded in the service's binary and applied by **Atlas** (pinned by version and by the hash of the binary): in a test, on a laptop and in a deployment alike, with Atlas's history table (`atlas_schema_revisions`) in the service's own schema and Atlas's own lock. They run explicitly — the chart's migrate job runs `atlas migrate apply` against the files in the image — and a service at start only checks that its schema is at the migration it was built with, waiting while it is behind and refusing to start if the schema is ahead. `--migrate-on-start true` applies them at start for laptops and tests. There are no down migrations in the directory; a mistake is fixed by a new migration, and an operator reverts with `atlas migrate down`, which plans the revert against a throwaway dev database. **Atlas does not notice a migration edited after it was applied** once the directory is hashed again, so the first build to see a version applied records the SHA-256 of the SQL it embeds (`venue_migration_sql`) and any later build holding something else refuses to start. | Changed 2026-09-17, after the owner asked for an established framework and rollback (it replaces a sixty-line runner of our own). Atlas applies the layout we already had, takes the same kind of advisory lock, and adds what we would otherwise write ourselves: `status`, `validate`, `lint`, and a planned revert that checks before it destroys — reverting a column with data in it stops rather than dropping it. The cost is a Go binary in the test path and in the image, pinned by hash in both, and a directory whose file names are Atlas's rather than ours. It was measured before it was chosen: `atlas migrate down` needs Atlas's naming (it refuses `V001__`), needs a dev database it owns, and silently accepts an edited migration whose sum was regenerated, which is why the checksum check stayed. | |
| S-3 | Each service has its own database, role and schema: `treasury`, `identity`, `parlays` and `oracle`. In the chart they share one PostgreSQL server; in production each URL may name a server of its own. The schema is named after the service in every case, and the role owns only its own database. | The blueprint asks for one PostgreSQL per domain (§18), with the ledger's the strictest. A database per service keeps that a change of host name rather than a data move, and a role per database makes "no service reads another's tables" a privilege rather than a convention. The fixed schema name keeps tests (a schema each on one server) and production the same code. | |
| S-4 | TLS defaults to libpq's `prefer`; `verify-full` with a CA file is the setting for any database reached over a network the venue does not control, managed ones included. The in-cluster server of the chart runs without TLS. | `prefer` connects to a laptop's server and to a managed one alike, which is what "configuration only" asks. It does not authenticate the server, so the chart's values for an external database say to set `verify-full`. The in-cluster server is reached over the pod network, which network policy confines to the owning services. | |
| S-5 | Database tests run against a real server when `VENUE_TEST_DATABASE_URL` is set, each in a fresh schema, and print a `skipping` line otherwise. `./check` starts one in a container (the chart's image, pinned by digest, on loopback, `fsync=off`) when Docker is usable and removes it when it ends. | Unit tests keep an in-memory store and stay fast; what only a database can show (constraints, triggers, transactions, reconnecting) is tested on one. A schema per test lets tests run in parallel on one server. | |

## Treasury

| # | Decision | Why | |
|---|---|---|---|
| S-6 | The file store is removed from the treasury, not kept as a test double: unit tests use an in-memory implementation of the same `Records` trait, which keeps the database's rules (a posting balances, is written once under its key, a transfer's terms never change) and can be made unreachable. Earlier books are moved with `venue-treasury import`. | Two stores of record would drift; the in-memory one is visibly a test double and cannot be selected by the binary. | |
| S-7 | Double entry and append-only are enforced in the database: a deferred constraint trigger checks at commit that each posting has at least two lines summing to zero; statement triggers refuse `UPDATE`, `DELETE` and `TRUNCATE` on every table of record; a row trigger refuses a change to a transfer's terms. `PUBLIC` holds no such privileges, but the owning role keeps them, because PostgreSQL's foreign-key checks need them; a separate read-and-insert role for the running service would close that and is left for when DevOps decides roles. | §11 asks for append-only, balanced, integer-cent postings; enforcing them where the data is keeps a bug, a script or a person with a SQL prompt from breaking them. Triggers bind the owner; revoking the owner's own privileges was tried and breaks every foreign key. | **needs review** |
| S-8 | A posting's idempotency key is its transfer and the accounts it moves money between, in order (`transfer:<id>:<debit>><credit>`), or `opening:<accounts>` for a seed grant. The same key with the same lines is a no-op; with other lines it is refused. `(account_id, client_transfer_id)` is unique. | Each step of a transfer (received, reclaimed, granted, paid out, returned) moves money between a pair of accounts no other step of it uses, so the key names the step without new code in the state machine. A key is what makes a write repeated after a lost acknowledgement safe. | **needs review** |
| S-9 | A transfer's current state is one mutable row with a version; every change is also a row of `transfer_events`. Only a change that differs from the row is recorded. | Reads need the current state; audits need every state; a repeated write must not add a spurious event. | |
| S-10 | The treasury keeps a working copy in memory, rebuilt from the records at start and read again after any failed write before anything else is written. Writes happen under the treasury's lock, before the state they record is acted on. The reconciliation invariant `ledger_sums_to_zero` sums the ledger in the database and checks the working copy against it. | The service's logic, tests and reconciliation stay as they were, reads need no round trip, and a write whose outcome is unknown cannot leave memory and records apart for longer than the next write. | |
| S-11 | When the database cannot be reached: new transfers, cancellations and break resolutions are refused with 503 and change nothing; transfers under way wait; reads come from the working copy; reconciliation is postponed and retried every 5 s; `/healthz` answers 503, so the pod leaves its Service and the gateway answers transfers with 503. At start the treasury retries with backoff and does not listen until it can connect. | Refusing is the only safe answer for money that cannot be recorded; taking the pod out of the Service makes the gateway's existing 503 the customer-facing answer. | **needs review** |
| S-12 | Timestamps are `timestamptz` (UTC) converted from the treasury's millisecond clock; reconciliation reports are `jsonb`; the fake bank's arrivals are a `timestamptz[]`. | Readable by anyone with psql, exact to the millisecond the code works in. | |

## Identity and accounts

| # | Decision | Why | |
|---|---|---|---|
| S-13 | An `accounts` table holds each account's ID, display name, the SHA-256 of its dev token (tagged `venue-dev-token/1:`) and when it was made, seeded from the catalogue at every start: new accounts added, names and tokens updated, none removed. No personal data; people and what identifies them go in tables of their own referring to it, later. The gateway still reads dev tokens from the catalogue. | The blueprint keeps the account-to-person mapping only in the accounts database and requires it to outlive every record that refers to it, so the table is keyed by the pseudonymous ID and never deletes. Seeding from the catalogue keeps test environments declarative. Moving dev-token checks into the service would change the gateway-facing API, which was to stay as it is. | |
| S-14 | Keys are rows the database keeps from being changed: a trigger refuses any change to a key's terms and any revocation undone or moved; deletes are refused. Only the last use moves. Secrets are never stored, only their hash (G-2). | A key cannot be changed, only revoked (G-6); the database is where that is cheapest to guarantee. | |
| S-15 | Keys are read into memory at start and verified from memory; writes go to the database first and are refused with 503 if they fail, after which the keys are read again before the next call. | Verification stays a lock and a hash, as G-7 assumes; re-reading after a failed write means a revocation whose acknowledgement was lost still takes effect. | |
| S-16 | When the database cannot be reached, `/healthz` fails, so the identity pod leaves its Service and gateways answer keys they have not verified in the last 5 s with 503; dev tokens keep working. Key changes answer 503. `--store memory` exists for tests and throwaway local venues, and says so when it starts. | The gateway already treats an unreachable identity service as 503 for uncached keys, which is the behaviour the owner described; keeping the service ready on memory alone would hide an outage in which no key can be made or revoked. | **needs review** |

## Parlays and the oracle

| # | Decision | Why | |
|---|---|---|---|
| S-17 | The parlay service keeps approved responders in `responders` and every change in an append-only `responder_changes` (who: catalogue, operator or import). The catalogue seeds the list once, recorded in `responder_list`. While its database is unreachable the service routes from memory and refuses changes with 503; it stays ready. | Approvals are an operator's decisions and worth a history; routing must not stop for a database blip, but a change that cannot be recorded would silently revert at the next restart. | **needs review** |
| S-18 | The dummy oracle persists every case whenever it changes, before acting on the change: the case row, and append-only reports, proposals, sign-offs, disputes and history; postponements and suspensions by hand too. A restarted oracle loads unsettled cases and the most recently settled ones, and sends again (under the same command ID) any `ResolveEvent` a case was sequencing. Times stay in the sequencer's nanoseconds. | Blueprint §12 lists resolution cases, evidence and sign-offs among the records kept in PostgreSQL. Writing before acting means a case's state is never ahead of what the records say; a repeated `ResolveEvent` is deduplicated (E-7.1). | |
| S-19 | While the oracle's database is unreachable, cases do not advance (a change that cannot be written is undone and its `ResolveEvent` not sent) and manual case actions, postponements and suspensions answer 503; the calendar keeps listing, starting and closing rounds, which the journal records. The schedule says cases are paused, and `/oracle/healthz` stays ready with a `database` field. | Pausing proposals is the owner's stated behaviour; the calendar's decisions are derived from the journal and lose nothing. | **needs review** |
