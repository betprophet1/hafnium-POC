# Engine scenarios

Each file is one scenario: a setup, then steps, each step an input and the exact results the engine must
emit for it, in order. They are the acceptance tests for any implementation of `../engine-spec.md`: the
reference model runs them with `../reference/run_scenarios.py`, and the Rust harness in `core/` runs the
same files against the Rust engine.

**Expected results are computed by hand from the specification**, with the arithmetic shown in the
scenario's `notes`. They are never generated by running an implementation. When an implementation and a
scenario disagree, decide from the specification which is wrong, fix that, and say which rule decided it.

## Format

```json
{
  "name": "…",
  "rules": ["E-10.6", "…"],
  "notes": ["arithmetic and reasoning, one line each"],
  "group": 1,
  "setup": [ … ],
  "steps": [ { "input": { "msg": "NewOrder", … }, "advanceNs": 0, "expect": [ { "msg": "OrderAccepted", … } ] } ]
}
```

- **Time.** The first input is at 1 800 000 000 000 000 000 ns; each later input is 1 ms after the previous
  one unless the step gives `advanceNs`. Sequence numbers count from 1 across setup and steps.
- **Setup** items are raw inputs (`"msg"`), or shorthands: `centTable` (ticks 0–98 are 1¢–99¢, so tick
  `t` is `t + 1` cents), `binary`, `categorical`, `parlay` and `fund`. Setup commands must all apply.
- **Defaults** for inputs: `sessionId` is `accountId × 10`; a `NewOrder` is `GTC`, entered as `YES`,
  cancelled at event start, with no flags, protection, spend cap, stake, group or expiry; `expiresAfterNs`
  sets `expiresAt` relative to the input's time; an `AmendOrder` leaves `atEventStart` `UNCHANGED`.
- **Defaults** for expected results: `sessionId` as above, fees 0, `originalOrderId` null and `rejectReason`
  `NONE` unless given.
- **IDs.** `"O3"` in an order ID field is the group's third order ID and `"T2"` in `tradeId` its second trade
  ID (E-2.8).
- `"expect": null` runs a step without checking it; `"expectFailStop": true` requires a fail-stop.
