# Decisions made to complete the engine specification

Each entry is a choice `engine-spec.md` needed and the blueprint did not make. They are defaults, not
settled policy: every one can change, and a change means editing the rule, the reference model and the
scenarios together. Entries marked **needs review** affect customers or the rulebook and should be confirmed
before anyone builds on them. Numbers are stable; gaps are decisions that were later folded into rules.

| # | Decision | Why | |
|---|---|---|---|
| D-1 | A void reverses every cash flow the event caused: each account is paid the negative of the net cash its fills and set burns in the event paid it, so every account ends as if it had never traded the event. Sale proceeds and releases are not held back, so a void can leave an account's available cash negative; the account can then receive cash but spend none until it is funded. | A void means the bets did not happen, and money goes back as if nothing was bet. Refunding current holders' cost basis cannot be paid once proceeds have been released: A buys YES at 40¢ against B's NO at 60¢ (pool $1.00) and sells that YES to C at 70¢; refunds would owe C 70¢ and B 60¢ from $1.00. Reversing every trade instead returns B 60¢ and C 70¢ and takes A's 30¢ gain back. Holding proceeds until resolution would make that collection certain, but voids are rare and collateral must keep moving across the venue; customers are identified, so a shortfall is a debt to collect. Confirmed 2026-09-15. | |
| D-2 | Each fill charges its maker and its taker `⌈r · yesCost(t, q) · noCost(t, q) / (100 000 000 · q)⌉` cents, `r` the party's rate in millionths: `r / 10⁶ × q × P × (1 − P)` dollars, rounded up to the cent, per fill (E-10.11). Maker and taker rates are separate, and both are 0 until `SetFeeSchedule` sets them. A maker rate may be negative, which is a rebate; rounding up makes a rebate never larger than the formula. A maker rate lies between −100% and 100%, a taker rate between 0 and 100%. Fees are credited to account 0 and rebates paid from it (D-21). | A fee proportional to `P(1 − P)` is what prediction-market exchanges charge today, commonly a 7% taker coefficient with a smaller maker one, so programmatic traders price it the way they already do. It is largest at 50¢ and vanishes toward certainty, as the contract's risk does. One rounding rule for both signs is the simplest to state and to implement: the ceiling never charges less than the schedule and never rebates more, so rounding never costs the exchange. Per fill, because the fill is what the engine clears and emits; an order split across fills can pay up to a cent a fill more than one computed on the whole order. Millionths state published coefficients such as 0.07 and 0.0175 exactly, and every intermediate fits a 128-bit integer. At 100% the fee is at most the cheaper side's cost, so the bound keeps a fee below what the contract is worth. Confirmed 2026-09-17. | |
| D-3 | Self-match prevention defaults to `CANCEL_INCOMING`. | The order being entered is the one the account is acting on; cancelling a resting quote silently is more surprising. No mode lets an account trade with itself: self-trading is not permitted on the venue. Confirmed 2026-09-15. | |
| D-4 | An amendment that reprices or increases loses priority and may trade immediately, keeping its order ID. | Cancel-and-replace semantics without forcing a new ID on market makers. Standard practice. Confirmed 2026-09-15. | |
| D-5 | Expiry is processed only on `TimeTick`, so its precision is the tick interval (1 ms). | Blueprint §4 makes ticks the engine's clock. | |
| D-7 | Holdings locks are taken only at acceptance and never increased later. | Simple and conservative: a position acquired after an order rests does not retroactively free that order's reservation. | |
| D-8 | Automatic set burns apply only to partition events (disjoint masks covering every state). Events with overlapping books release nothing automatically. | Burns are final and safe; releases against overlapping books are floor advances, which blueprint §7 schedules for phase two. | |
| D-9 | A set burn runs after any fill touching the account in the event, on every spare complete set the account holds. | Money no outcome can take away goes back at once rather than at resolution. Money-neutral: selling later from nothing costs the same as selling from the set. A void reverses the release with the rest of the event (D-1). Complete sets form only by trading (D-24). Confirmed 2026-09-15. | |
| D-10 | Auto-pull and order-group triggers take effect at the end of the unit, after matching. | Lets `FOK` and capacity checks be decided by a dry run on the book alone; a mid-walk cancellation would make a dry run disagree with the real walk. | |
| D-11 | Rule limits count per whole second of sequencer time. | Deterministic, fixed-size state. Sliding windows can come later without a schema change. | |
| D-12 | Client order IDs are remembered for two hours by default; a rejected order still consumes its ID. Each entry expires under the window in force when it was recorded; changing the window affects only later entries. | Blueprint §13 requires a published window; consuming on rejection makes a resend's outcome identical to the original's. A fixed expiry lets an implementation drop expired entries unobservably: when entries were compared against the current window, lengthening it revived entries an implementation had already dropped (found by differential testing of the Rust engine). One window serves the whole venue and is published; a change is rare and taking effect as entries turn over is acceptable, since most markets live a few days. The window exists for idempotent resend after an uncertain outcome, so what it has to cover is a client's reconnect and retry horizon, not a trading day. It is also what sizes the duplicate table, which is fixed and holds `window × new orders a second` entries at about 176 bytes each; the table fail-stops rather than evicting, so the window is a capacity decision as much as a customer-facing one. At the ~57k new orders a second one node sustains, 24 hours would want ~4.9 billion entries. Two hours keeps resend safety far past any reconnect at a twelfth of the space. Confirmed 2026-09-15; shortened from 24 hours 2026-09-16. | |
| D-13 | Order and trade IDs are `(group << 48) + n`. | Unique across groups without coordination. | |
| D-15 | The protection band is measured from the raw best opposite tick, including the account's own orders. | The touch the customer sees; excluding own orders would need a queue walk. | |
| D-16 | A spend cap counts gross price in entered terms, and an order whose cap cannot buy one lot at its effective limit is rejected. | Matches how a stake is understood; the one-lot check is decidable without walking the book. | |
| D-17 | The position limit checks the worst case: position plus every resting order on the same side plus the new order. | Cannot be exceeded by any sequence of fills. | |
| D-18 | Closed-only mode applies to new orders only; resting orders are not altered when it is switched on. | Changing resting orders is what a mass cancel is for. | |
| D-19 | A mass cancel with nothing in scope emits no result. | The gateway acknowledges from the committed input, not from a result. | |
| D-21 | Account 0 is the exchange's own account: the settlement reserve and the fee account. Settlement leaves no remainder, so in v0 it receives nothing from settlement. It receives every fee and pays every rebate (D-2), so its available cash may be negative (E-3.3). It may not submit orders. | Blueprint §11's account tree includes a settlement reserve. It took rounding remainders while voids paid state-weighted values; D-1's reversal pays out collateral exactly. Fees need the exchange's side of every fill in sequenced state: crediting one account keeps fee income in the group's sleeves, visible in `SleeveChanged` beside the per-fill fee fields a ledger sums, and swept with `SleeveAdjust` like any other balance. The ledger's account tree separates fee income from the settlement reserve by source, so the engine needs no second account for it. | |
| D-22 | A parlay is listed under its own two-state event; `ExpireParlay` resolves that event to its losing state. | Reuses resolution rather than adding a second settlement path. | |
| D-23 | Closing a market removes its resting orders. | Blueprint §6: orders must not accumulate in books nobody can trade. | |
| D-24 | There is no basket mint or redeem: contracts are created and destroyed only by fills and set burns. The blueprint's explicit basket primitive (§7) is replaced. | Trading already creates contracts when two people open opposite positions, and set burns return complete sets. The primitive existed to save market makers capital when quoting every outcome; portfolio margining (blueprint §8) does that properly and is coming soon. Confirmed 2026-09-15. | |
| D-25 | Command IDs are remembered for seven days; a rejected command still consumes its ID. The window is fixed, not a group parameter. | E-7.1 made a command ID permanent, so the command set grew with every command the venue ever processed, and a fixed-size table fail-stops when it fills: every account funding takes an entry, so a table of 65 536 lasts a few weeks at a few thousand grants a day. Command IDs exist for at-least-once delivery — the outbox relay resends until it sees `CommandApplied`, and the ID makes a resend a `DUPLICATE` — and some commands move money, so a resend arriving after its entry expired would apply twice. The window must therefore outlast any sender's retry horizon, which is why it is days rather than the two hours of D-12; a sender must never resend a command older than it. Operator traffic is small, so a week of it is a small table. Fixed rather than a parameter, so there is no schema change and no window change to reason about. Confirmed 2026-09-16. | |
| D-26 | Fees are charged when a fill happens and are neither reserved nor checked before an order is accepted or amended. A fee can take an account's available cash below zero; the account can then receive cash but spend none until it is funded (E-3.3). | Reserving fees would put the fee rule into every reservation, amendment and spend cap, and the rate a resting order will pay depends on whether it ends up maker or taker and on overrides that can be set or expire while it rests, so a reservation could only be an upper bound that ties up cash. A fee is a few percent of a trade at most, customers are identified, and a shortfall is a debt collected the way a void's is (D-1). The cost is that available cash no longer stays at or above zero by construction: E-3.3 now allows exactly the fees an input charged and nothing else, so an implementation still fail-stops on any other shortfall. Confirmed 2026-09-17. | |
| D-27 | The fee schedule can be overridden. An override names an account, an instrument and an event, each 0 for any, both rates, a priority and optionally an expiry in sequencer time. For each party to a fill separately, the active override that matches it with the lowest priority wins, ties to the lowest override ID; with none, the default schedule applies (E-10.12). An override has no start time. | Precedence works like a routing table's metric: the operator states it on each override rather than the engine inferring it from which fields are set, so a market promotion meeting an account's negotiated rate is never an undecided case, and a tie falls to an ID the issuer chose. Each party resolves against its own account because a fee is an agreement with that account; the counterparty's terms must not change it. Expiry is a sequencer time the engine compares with `now`, so a promotion ends at a known log position without a second command, and an expired override is simply never chosen. The examples that shaped it: a market without fees for a day is `accountId` 0, its `instrumentId`, both rates 0 and `expiresAt` a day ahead; an account without fees forever is its `accountId`, both rates 0 and no expiry, at a priority below any promotion that should not apply to it. A start time is left out because a promotion can be sent when it starts. Confirmed 2026-09-17. | |
| D-28 | A void returns the event's fees and takes back its rebates, with the rest of its cash (D-1). | A void means the bets did not happen, and a fee on a trade that is reversed would charge for nothing. Fees enter the event cash of the paying account and of account 0 in equal and opposite amounts (E-10.11), so D-1's reversal returns them without a second mechanism and leaves the event's collateral untouched (E-15.6). Confirmed 2026-09-17. | |
| D-29 | A resolved or voided event, with its instruments, is released seven days after its resolution by default: `settledRetentionSeconds` (`SetListingParameters`, E-7.12) is a group parameter in sequencer time, counted from the input that resolved the event and applied as it stands at each tick, and a demo venue sets minutes. A tick releases at most one event, the earliest resolved, and emits `EventReleased` (E-8.4). A released event and its instruments are as if never listed: an order is rejected `UNKNOWN_INSTRUMENT`, a command `INVALID_COMMAND`, and the IDs may be listed again as new markets. Accounts, the duplicate table, the command set, rule limits, order groups, maker protection settings and fee overrides are not released, so a setting naming a reused ID applies to the new listing; listers are expected not to reuse IDs. Seven days leaves room for disputes to be dealt with. Confirmed 2026-09-17. | The engine's tables are fixed, and a venue that lists a round of every market every few minutes filled them in hours and then could only stop. A settled market needs nothing more from the engine: its positions are paid and zero and its orders gone (E-15.5), so the engine only has to keep it long enough for everything around it to finish with it, and releasing it changes no position, sleeve or book. The time is not the dispute window: blueprint §11's window runs before `ResolveEvent` is sequenced, a resolution is final in the engine (E-15.3), and a correction after payout opens an operator case rather than resettling (blueprint §14). Seven days is what readers, the parlay service, the ledger and an operator's case get to see the settled market addressable by ID with its final state and rejections that say it is resolved, and it matches the command window (D-25), so a resend of the resolution within it is a `DUPLICATE` rather than an `INVALID_COMMAND`. A reversal of a payout, if the venue ever adds one, would have to act within the retention, and after it is impossible by construction; that is intended, because the market's cash was already settled and discarded at resolution (E-15.5). Counting from the resolution, the only input that settles an event, gives every replica the same moment; applying the retention in force at the tick (rather than recording an expiry, as D-12 does) keeps releases in resolution order, so a queue suffices and a shortened retention releases the backlog in order. One event a tick bounds a tick's work by one event's instruments while releasing up to a thousand events a second at production cadence. IDs are not remembered after release because that would grow without bound again; the demo's IDs never repeat. | |
| D-30 | Listings are limited by sequenced group parameters, `maxEvents`, `maxInstruments` and `maxPriceLevels` (twice the rows of each carried instrument's tick table), 0 meaning none. A `DefineEvent` or `ListInstrument` past one is rejected `LISTING_CAPACITY` after its other checks; nothing already listed changes when a limit is lowered. Storage running out is still a fail-stop (E-18.3), and an operator sets the limits at or below the capacity profile every replica runs. | A rejection has to be a function of the journal (E-1.1), and table sizes are node configuration, so rejecting when storage is full would let replicas with different profiles disagree; this is how `activeOrderLimit` already turns the order slab's fail-stop into `ORDER_CAPACITY`. Price levels are limited separately because a book reserves two levels per tick-table row whether it uses them or not, so on a node with 131 072 levels a parlay ladder of 279 rows uses up levels long before instruments run out. Capacity is checked after validity, so an invalid listing is reported as invalid whatever the venue carries. With releases (D-29) the limits are a steady state rather than a lifetime: the storage a release frees is reusable by any listing (E-18.3), which an implementation with a bump-allocated level pool satisfies by compacting it when a listing does not fit at its end. | |
| D-31 | A snapshot carries the engine's **logical** state only (§20): what the rules of this specification observe, and nothing an implementation arranged. It carries no slab slot, pool offset, free list, hash position, ring head or table size, and none of the residue a running engine accumulates — records in the duplicate, command and GTD windows whose entries have gone, and fee overrides that have expired. Entries at their initial value are not written at all. | Two engines this specification cannot tell apart must snapshot identically, or the equivalence property (E-20.9) is not a property but a coincidence of history: every one of those things differs between engines that have reached the same state by different routes. The residue is invisible to every rule here except `FailStop::Capacity` (E-18.3), and the omission runs the safe way — a restored engine holds none of it and so has at least as much room as the engine it came from, which can postpone a capacity fail-stop but never bring one forward. Carrying the residue instead would make the snapshot a picture of one engine's history rather than of the venue's state, and would be a faithful copy of a thing nobody wants copied. |
| D-32 | A snapshot is taken by an engine replaying the journal, never by the engine serving traffic, and never during an input. It is written into the journal (`Snapshot`, template 53) rather than beside it, with the sequence of the input it follows. | Blueprint §4 asks that the hot path never pause to serialise itself, and replay is deterministic, so a snapshot taken by a replaying engine is the snapshot the serving engine would have taken — which is what E-20.9 says. Writing it into the journal is what makes the journal cuttable: a reader, or a recovering node, can begin at a snapshot instead of at sequence 1, so everything before one may be archived and removed. Beside the journal it would be another file to keep in step with it, and the pair could be separated by exactly the operations archiving performs. |
| D-33 | An account may name another account as its **master**, set once when the subaccount is created and never reassigned; a master names none. Self-match prevention (E-13.1) compares the two accounts' effective master — an account with none is its own — rather than the accounts themselves: an account and any subaccount of the same master, and any two subaccounts of the same master, are prevented from matching under the mode of the account whose resting order is hit, exactly as an account is prevented from matching itself today (D-3). Rule limits, positions, margin, maker protection and fee overrides stay keyed by the account's own `accountId`; only the self-match comparison widens. | The owner's decision (2026-09-25): a market maker's subaccounts (a liquidity-provision book and a scalping book, say) must never be able to trade against one another — this is a regulated venue, so it is a necessity and not a convenience, and it is exactly what self-match prevention already exists to forbid for a single account (D-3); a subaccount family is one party for that rule and nothing else. Keeping risk (limits, positions, margin) per subaccount is what makes subaccounts worth having — a firm wants its strategies to net risk separately, not share one book — so only the matching rule, not the account's whole identity, widens. **needs review** — landing this needs a rule change to E-3.2 and E-13.1, a `masterAccountId` field in the journal schema (`interfaces/sbe/venue-journal.xml`), a reference-model update and a scenario that fails before the change and passes after, per `AGENTS.md`; this entry records the decision ahead of that change, not the change itself. | |
| D-34 | The engine gains no new command for moving cash between a master's accounts. A transfer between two accounts of the same master is a `SleeveAdjust` `RECLAIM` from one and `GRANT` to the other (E-7.2), issued by a service exactly as cross-group sleeve work already is (E-1.2), never by the engine itself. | E-1.2 already puts sleeve top-ups outside the engine's own state machine, because each engine is one deterministic state machine per sequencer group (E-1.1) and cannot see a second group's state to move money into it atomically; the treasury already runs this exact reclaim-then-grant sequence for deposits and withdrawals, so an internal transfer needs a new orchestration in the treasury, not a new primitive in the engine. Recorded here so nobody proposes an atomic `SleeveTransfer` command believing it is missing; it would only be needed if two groups' engines had to agree within one input, which the architecture does not allow. Confirmed 2026-09-25. | |
